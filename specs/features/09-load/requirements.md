# Feature 9 requirements: Load

## Requirements from the sources

- R1. A load test measures the limits on clients, samples, and payload size. (roadmap feature 9; N12)
- R2. The test runs against the cloud server only. It does not use the Docker server or the test source. (roadmap feature 9)
- R3. I change the server settings with the admin API while the server runs. (roadmap feature 9; feature 6, R1)
- R4. The Makefile has three new targets that call the admin API of the cloud server with curl. `make cloud-pause` pauses the stream, `make cloud-resume` resumes it, and `make cloud-setting-update` changes the settings. (roadmap feature 9; N13)
- R5. Each step of the test has 3 runs, and each run is 30 s. (roadmap feature 9)
- R6. A run passes when the p99 of the total latency from `latency.report()` meets the 100 ms target and the client stays at 54 fps or more. (roadmap feature 9; N6; feature 8, G5)
- R7. The first part sets the samples per second to 20,000, then 100,000, and then 1,000,000, and it stops at the first step that fails. (roadmap feature 9)
- R8. The second part raises the number of clients until a step fails. (roadmap feature 9)
- R10. The highest samples per second that passes becomes the new default. (roadmap feature 9)
- R11. The feature adds the limits and the new default to docs/results.md. (roadmap feature 9; N12)
- R12. The README and the three logs in docs/ record this feature. (roadmap, S2, S3, S7, N14; CLAUDE.md)

## Items the sources do not cover

The roadmap leaves three decisions to this plan. They are the token and the values of the three targets, the result of a step from its 3 runs, and the steps of the second part. Each item from G1 to G9 was my proposal, and the user answered each one. The user did not see G10 and G11 as questions. G12, G13, and G14 are changes that the user made in the review of the plan. G15 is a change that the user made in the validate session.

- G1. **Agreed.** The three targets read the admin token from the shell variable `CLOUD_ADMIN_TOKEN`. I export it once in the terminal with the two AWS CLI commands in the README section Deploy. A target stops with a message when the variable is not set, and it sends no request. The token is not in the repo, and these three targets make no AWS call. The recipe does not print the token.
- G2. **Agreed.** `make cloud-setting-update` takes the make variables `SAMPLES_PER_SECOND`, `BATCH_INTERVAL_MS`, and `MAX_VALUE`, which are the names that `make docker` uses. The target sends only the variables that are set, such as `make cloud-setting-update SAMPLES_PER_SECOND=100000`. It stops with a message when none is set. Each of the three targets prints the reply of the server, and it fails when the status is not 200. The server checks the ranges, so the Makefile does not. The server address is the make variable `CLOUD_SERVER`, and its default is https://api.precision.jgangjee.com.
- G3. **Agreed.** I time a run and read its frame rate with a snippet that I paste into the DevTools console. The snippet is in validation.md, and the repo code does not change. `run()` calls `latency.reset()`, counts the animation frames in windows of at least 1 s for 30 s, as the side panel does, and calls `latency.report()`. It gives the p99 of the total, the lowest frame rate of the windows, the number of batches, and the round trip of the clock request. `step()` does 3 runs and prints one table. I added two values after the user agreed. The first is a flag that is true when the tab was hidden during the run. The second is the start time of the run, which matches the run with a row of the CPU table from G13.
- G4. **Agreed with a change.** I proposed that a step passes when 2 of its 3 runs pass. The user asked for 3 full runs. A step passes when all 3 runs pass. A run with an obvious error in the setup, such as a hidden tab, does not count, and I run it again.
- G5. **Agreed.** In the second part, one Chrome tab measures, and each other client is a curl process on the laptop that reads the stream and drops the data. A shell loop in validation.md starts and stops them. The steps are 2, 5, 10, 20, 50, and 100 clients in total. The part ends at the first step that fails, or at 100 clients. Every client shares my home link, so the link can set the limit before the server does, and docs/results.md says so.
- G6. **Changed.** I proposed that the second part runs at the highest rate that passes the first part. The user chose 20,000 samples per second, so the numbers line up with the feature 8 runs.
- G8. **Changed.** I proposed that the implement step changes the default when a rate above 20,000 passes. The user chose to decide after the test. This feature changes no default. docs/results.md gives the highest rate that passes, and it names no new default. The change of the default goes to the replan. R10 and the new default in R11 are open until then. In the replan, the user kept the default at 20,000 samples per second, and docs/results.md says so.
- G9. **Changed.** I proposed that I run the load test in the implement session, as in feature 8. The user chose the validate session. The implement session adds the three targets and the README text. In the validate session I run the three parts as manual checks and paste the result of each step, and the AI writes the feature 9 section of docs/results.md.
- G10. **From the user request for this plan.** The user asked to limit the code. The Makefile targets are the only new code. The feature changes no file in backend/, frontend/, or infra/, and it adds no test file. The checks of the targets are commands in validation.md.
- G11. **Not asked.** The run conditions follow feature 8, G5. The client runs from `make frontend` in Chrome with Energy Saver off, with N = 32, the tab in front, and a max value of 10,000. The first part uses one client and a batch interval of 50 ms. The pass rule reads the p99 as it is, with no margin for the error of the clock offset, and docs/results.md gives the round trip. The server can drop a batch for a slow client, and a batch that does not arrive gives no latency sample. The number of batches is not part of the pass rule, and docs/results.md gives it next to the expected number for each run.
- G12. **Changed by the user.** The first part runs 20,000, then 250,000, then 500,000, and then 1,000,000 samples per second, and it stops at the first step that fails. This replaces the steps in R7 and in the roadmap, which has 100,000 in place of 250,000 and 500,000. The user tested 100,000 before this plan. The step at 20,000 is the baseline. At a batch interval of 50 ms, the batches hold 1,000, 12,500, 25,000, and 50,000 integers, which is about 5 KB, 61 KB, 122 KB, and 244 KB.
- G13. **Added by the user.** A fourth target, `make cloud-cpu`, prints the CPU use of the cloud service from CloudWatch, as a clue to what limits a step. The user did not see the details below as questions. The target reads the cluster name and the service name from the outputs of the stack `PrecisionStack`, and it reads the `CPUUtilization` metric of the service from the `AWS/ECS` namespace. It prints one row for each minute of the last 30 minutes, with the time, the average, and the maximum in percent of the 0.25 vCPU of the task. `MINUTES` changes the 30. The target uses the AWS CLI with the profile and the region of the deploy, and it needs no admin token. CloudWatch has one value for each minute, and a value shows about 2 minutes late. A step is about 90 seconds, so I read the table after each part, and one row can hold parts of two steps. The CPU is a clue and not part of the pass rule.
- G14. **Added by the user.** The load test ends with `make cloud-pause` or `make destroy`, so the server does not cost more than it must when I leave it overnight. I choose one of the two at the end of the validate session. A pause stops the data transfer and leaves the stack running. A destroy stops every cost, and the server needs `make deploy` before a reviewer uses it. M4 holds the step.
- G15. **Removed by the user in the validate session.** The plan had a third part that raised the batch interval through 100 ms, 500 ms, and 1 s, with one client at 20,000 samples per second. The user removed it before it ran, and said that it proves nothing. Two facts agree with that. The total latency starts at the `started` time of a batch, so a longer interval adds no wait to it. The largest batch of the third part held 20,000 integers, and the first part passes with 50,000. The test now has two parts, and the first part gives the payload size for R1. R9 and G7 held the third part, so those two numbers are no longer in this file. The roadmap had the third part until this change, and it now names two parts.
