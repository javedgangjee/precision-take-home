⏺ The backend now stops within 3 seconds, even when a stream is open.

  Cause: An SSE stream never ends by itself. On shutdown, Uvicorn waits for
  every open connection to close, so with a browser or curl connected it waited
  forever.

  Fix: I added --timeout-graceful-shutdown 3 to the backend target in
  Makefile:18. After 3 seconds, Uvicorn cancels the open streams. Then the app
  shutdown runs and the broadcaster task stops.

  Check: I ran make backend, opened /stream with curl, and sent Ctrl+C. The
  server exited in 3 seconds and the app shutdown completed. Uvicorn logs one
  line, ERROR: Cancel 1 running task(s), timeout graceful shutdown exceeded.
  That line is expected when it cuts off a stream.

  I added an entry to docs/ai-changes.md and one to docs/trade-offs.md, and a
  sentence to the make backend line in the README. make dev gets the fix too,
  because it calls make backend. There is no Dockerfile yet. When feature work
  adds one, its Uvicorn command will need the same flag.

  the client do. Explain it plainly

⏺ The server keeps the average rate right. It does that by sending late batches
  in a burst. The client has no code yet, so right now it does nothing special.

  How the server paces batches

  The broadcaster plans each batch at a fixed time from when it started
  (backend/app/broadcaster.py:55). With the defaults, batch 1 is due at 50 ms,
  batch 2 at 100 ms, and so on. Every batch holds the same number of samples,
  which is 5,000 with the defaults. The count comes from the batch number, not
  from the clock. The server never makes a smaller or larger batch to make up
  for lost time.

  A short slowdown

  Say the CPU stalls for 200 ms. Four batches miss their times. When the CPU
  comes back, the sleep time is zero, so the server makes those four batches one
  after another with no wait. Then it goes back to one batch every 50 ms.

  The effect on the rate is that one short gap has no samples, then a burst
  carries the missing samples. Over any second or two the total is still 100,000
  samples a second. The rate is uneven over short periods but correct over
  longer ones.

  A slowdown that does not end

  Say the CPU is so slow that one batch takes more than 50 ms to make. The
  server then never catches up. It makes batches as fast as it can, with no
  sleep between them, and falls further behind every second. The real rate drops
  to whatever the CPU can manage. The server makes no batches of its own. It
  keeps a debt of missed batches that it will pay back later.

  After a long stall

  This is the weak point. If the machine sleeps for an hour, the server owes
  72,000 batches when it wakes. It makes all of them back to back, which uses
  the whole CPU for a while and sends a flood of old data. docs/trade-offs.md
  mentions this cost, but no code limits it. A common fix is to skip missed
  batches after a gap longer than a set limit, and restart the schedule from
  now. I can add that if you want it.

  What reaches the client during a burst

  Each client has a queue of 2 batches. When a burst comes faster than the
  client's connection takes it, the queue drops the oldest batch to make room.
  So the client gets the newest batches and misses some older ones. Other
  clients are not affected.

  The client can see what it missed, because each batch has a sequence number in
  the SSE id field. A jump from 41 to 45 means that batches 42 to 44 were
  dropped. The client cannot see that a batch is late, because batches carry no
  timestamp. The roadmap leaves that for feature 7.

  What the client does now

  It does nothing yet. The frontend is still the scaffold. In frontend/src/app
  nothing opens /stream. When the frontend exists, the browser's EventSource
  fires one message event for each batch as it arrives. A burst will show up as
  several events close together, followed by a normal pace again. Whether the
  client redraws for each one or only draws the newest is a choice for the
  frontend feature.

❯ Any variations of the cors origin that I would need to cover?                 

  Ran 1 shell command (ctrl+o to expand)

⏺ Yes, a few. Starlette compares each origin as an exact string, so the scheme,
  the host, and the port must all match. The server reads CORS_ORIGINS in
  backend/app/settings.py:31. It splits the value on commas and trims spaces,
  and changes nothing else.

  Local development
  - 127.0.0.1: A browser at http://127.0.0.1:4200 sends that origin, and it does
    not match http://localhost:4200. You need both only if you open the app by
    IP.
  - Another port: If ng serve moves to 4201 because 4200 is busy, the origin
    changes and the stream fails. The Makefile sets the port to 4200, so this
    matters only when you run ng serve yourself.
  - A trailing slash: A browser never sends a trailing slash in Origin. If
    someone sets CORS_ORIGINS=http://localhost:4200/, nothing matches and the
    stream fails with no clear error. I can make load_settings strip a trailing
    slash, which is a one-line change.

  Deployment (feature 5)
  - The frontend's public origin: This is the value that matters most. The
    roadmap puts the backend at your domain but does not say where the frontend
    is hosted.
    - If the frontend is on its own origin, such as https://app.yourdomain or a
      CloudFront URL, that exact https:// origin must be in the list.
    - If the ALB serves the frontend and the backend on the same origin, the
      browser does not use CORS for the stream, and the setting does not matter
      there.
  - www and no www: If both names serve the frontend, list both, or redirect one
    to the other.
  - http and https: If the site can load over plain http before a redirect, that
    origin differs from the https one. A redirect to https at the load balancer
    solves this.

  One to test in feature 4
  When EventSource reconnects, the browser adds a Last-Event-ID header. I am not
  sure that every browser skips the preflight check for that header. If one
  sends a preflight, it will fail, because the middleware allows no extra
  headers. Adding allow_headers=["Last-Event-ID"] would cover that case at no
  cost. The reconnect tests in feature 4 should check this in Chrome, Firefox,
  and Safari.

  I recommend two changes now: strip trailing slashes, and add Last-Event-ID to
  the allowed headers. Tell me if you want them.
