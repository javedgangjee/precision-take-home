# Roadmap

Every feature updates the README and the three logs in docs/ as it goes. That work covers S1 to S7 and N14 across all features.

1. **Scaffold.** The goal is a repo where the backend, the frontend, and the CDK app exist, the tests run, the linters pass, and the CDK app synthesizes, all from the Makefile. It covers N13 and S2. The status is done.
2. **Backend.** The goal is a FastAPI server that generates random integers and sends them in batches over Server-Sent Events. The backend allows cross-origin calls with CORSMiddleware. It reads the allowed origins from an environment variable, and the default is http://localhost:4200. It covers B2, N5, N7, N8, and N11. The status is done.
3. **Frontend.** The goal is an Angular client that bins values, keeps counts, and draws the grid, the axis labels, the color scale, and the side panel. It covers B1, B3, B4, B5, B6, N1, N2, N3, N4, D2, and D3. The status is done.
4. **Stream.** The goal is a client that shows the stream state, reconnects with backoff, and keeps counts on screen during a reconnect. The feature also adds a Dockerfile for the backend and a Makefile target that runs the stream in Docker Desktop on my laptop, so the client can connect to the same image that feature 5 deploys. It covers N9, N10, and D1. The status is done.
5. **Deploy.** The goal is the backend running on ECS Fargate behind an ALB at my domain, deployed with CDK from the Makefile. It covers B2 and N13. The status is done.
6. **Admin API.** The goal is a set of backend HTTP endpoints that change the stream settings while the server runs, so that a test of a new sample rate needs no restart. The feature has no admin web page. An HTTP request sets the samples per second, the batch interval, and the maximum value, within the ranges in N11. An HTTP request can also pause and resume the generation. While paused, the server sends no batches, the batch sequence number does not advance, and the server heartbeat keeps each connection alive. The feature sends no new events to the client and changes no client code. It covers no required item. The status is done.
7. **Settings Display.** The goal is a client that shows the live stream settings, the pause state, and the batches it missed. The server adds one new packet type, which is the settings packet. One settings packet holds the samples per second, the batch interval, the maximum value, and the pause state. The server sends the settings packet to a client when the client connects, and to every client when a setting or the pause state changes. The server has no separate init, update, or pause message. The settings packet is not a batch. It carries no sequence number, and the batch sequence number does not advance when the server sends one. The missed batch count reads only the batch ids, so a settings packet never adds to it. The server queue that drops the oldest batch for a slow client does not drop a settings packet. The side panel shows the three settings and updates them when a settings packet arrives. A client that gets a settings packet with the pause on stops its 5 s watchdog, keeps the stream open, and shows Paused in the badge. A settings packet with the pause off starts the watchdog again. The client reads the batch sequence number from the id of each batch and counts the batches it missed, both inside one connection and across a reconnect. When an id skips ahead, the client adds the size of the gap to the missed batch count. When an id is lower than the last one, the server has restarted, and the client resets the missed batch count to 0. The side panel shows the missed batch count. It covers N10 for the Paused state and N5 for the missed batch count, and no other required item. The status is done.
8. **Latency.** The goal is a measured latency from generation to render. The server takes a timestamp at each stage of its work, from generation to send. It does not put the timestamps in the batch data, so the data stays a JSON array of integers. It puts them in the `id` field of the batch event, after the batch sequence number, in the form `<sequence number>:<started>:<encoded>:<sent>`. The client reads the sequence number from the first part of the id, so the missed batch count from feature 7 still works. The client adds a timestamp at each stage of its work, from receipt to render. The client calculates the total latency from generation to render. The side panel does not show the latency. The plan for this feature names the stages, sets the exact form of the id, decides how to compare the server clock with the client clock, and decides how I read the measured times from the client. The feature writes docs/results.md, which gives the measured time for each stage and compares the total with the 100 ms target in N6. It covers N6. The status is done.
9. **Load.** The goal is a measured set of limits from a load test. The test runs against the cloud server only. It does not use the Docker server or the test source. I change the server settings with the admin API from feature 6 while the server runs. The feature adds three Makefile targets that call the admin API of the cloud server with curl. `make cloud-pause` pauses the stream, `make cloud-resume` resumes it, and `make cloud-setting-update` changes the settings. The plan for this feature decides how the three targets get the admin token and the new values. Each step of the test has 3 runs, and each run is 30 s. A run passes when the p99 of the total latency from `latency.report()` in feature 8 meets the 100 ms target in N6 and the client stays at 54 fps or more. The plan decides how the 3 runs give one result for a step. The test has three parts, in this order. The first part sets the samples per second to 20,000, then 100,000, and then 1,000,000, and it stops at the first step that fails. The second part raises the number of clients until a step fails. The third part raises the batch interval until a step fails. The plan sets the steps of the second part and the third part. The highest samples per second that passes becomes the new default. The feature adds the limits and the new default to docs/results.md. It covers N12. The status is in progress.
10. **Submission Check.** The goal is a repo that holds every document the submission needs, checked against the brief and the project overview. I add the documents to the repo, including the write-ups for B7 and B8. The AI then checks each requirement in the brief and the project overview against the repo and writes docs/submission-checklist.md. The checklist gives each requirement, the file that meets it, and a status of met or missing. The AI does not write the missing documents. It covers the check of B7, B8, and S1 to S7. The status is planned.
