❯ Is there a sequence number for the batches or a timestamp                     

⏺ No, the current plan has neither. Each event carries only the JSON array in
  its data field, with no event name and no id: field (G1). The client cannot
  tell that a batch was dropped, and it cannot tell how old a batch is.

  I recommend adding the sequence number now and leaving the timestamp for
  feature 7.

  - Sequence number: The server would put a counter in the standard SSE id:
    field, and the data would stay a plain array. The client could then count
    dropped batches. That matters more now that each client's queue holds only 2
    batches. The browser also sends the last id back when it reconnects, but
    the server can ignore it, because delivery is lossy (N7).
  - Timestamp: To carry one, the data would have to change from an array to an
    object, such as {"t": ..., "values": [...]}. Its only use is the latency
    measurement in feature 7 (N6). The server clock in the cloud and the
    reviewer's laptop clock will differ, so a raw server timestamp cannot
    measure latency to 100 ms on its own. Feature 7 has to solve that anyway, so
    the payload format is better decided there.

  Do you want me to add the sequence number to G1, the plan, and V4?
