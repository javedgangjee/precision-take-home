⏺ CORS is not needed yet, and no spec covers it. So nothing would add it later
  unless you ask for it.

  Why it is not needed yet: The scaffold frontend never calls the backend. The
  only endpoint is GET /health. The scaffold validation checks it with curl
  (specs/features/01-scaffold/validation.md:59) and opens the Angular page
  separately. A browser applies CORS only when a page on one origin calls
  another origin. That first happens when the client opens the SSE stream, and
  the stream arrives in feature 2 or 3.

  Why it is a gap: No spec mentions CORS, origins or a dev proxy.
  specs/tech-stack.md says the frontend runs only on the local machine, and
  feature 5 puts the backend at a jgangjee.com subdomain. So the client at
  http://localhost:4200 must call the backend at localhost:8000 during
  development, and the cloud backend after deploy. Both of those calls cross
  origins.

  You can handle this in one of two ways:

  1. Use CORS on the backend (my recommendation): FastAPI's CORSMiddleware would
     allow a list of origins read from an environment variable, with
     http://localhost:4200 as the default. The same code works locally and on
     Fargate, and SSE works through it with no extra setup.
  2. Use an Angular dev proxy: A proxy.conf.json would send /api calls through
     ng serve, so the browser sees a single origin and the backend needs no
     CORS. You would change the proxy target to the cloud URL after deploy. This
     can also buffer the SSE stream, which would affect the latency you measure
     in feature 6.

  I suggest option 1, and I suggest adding it when you plan feature 2, because
  that feature creates the stream endpoint. I can add a note to the feature 2
  line in specs/roadmap.md so the plan does not miss it. Do you want me to add
  that note?
