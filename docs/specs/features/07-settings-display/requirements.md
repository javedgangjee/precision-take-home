# Feature 7 requirements: Settings Display

## Requirements from the sources

- R1. The server adds one new packet type, which is the settings packet. One packet holds the samples per second, the batch interval, the maximum value, and the pause state. The server has no separate init, update, or pause message. (roadmap feature 7; user request for this plan)
- R2. The server sends the settings packet to a client when the client connects, and to every client when a setting or the pause state changes. (roadmap feature 7)
- R3. The settings packet is not a batch. It carries no sequence number, and the batch sequence number does not advance when the server sends one. The missed batch count never counts a settings packet. (roadmap feature 7; N5; user request for this plan)
- R4. The server queue that drops the oldest batch for a slow client does not drop a settings packet. (roadmap feature 7; N7)
- R5. The side panel shows the samples per second, the batch interval, and the maximum value, and it updates them when a settings packet arrives. (roadmap feature 7; N11)
- R6. A client that gets a settings packet with the pause on stops its 5 s watchdog, keeps the stream open, and shows Paused in the badge. A settings packet with the pause off starts the watchdog again. (roadmap feature 7; N10; feature 4, G5)
- R7. The client reads the batch sequence number from the id of each batch and counts the batches it missed, both inside one connection and across a reconnect. A gap in the ids adds its size to the count. An id lower than the last one resets the count to 0. (roadmap feature 7; N5)
- R8. The side panel shows the missed batch count. (roadmap feature 7)
- R9. The counts stay on screen during a pause and during a reconnect. (N9)
- R10. The batch events, `GET /health`, and the four admin endpoints stay as they are. (feature 2, G1; feature 6, G2 and G3)
- R11. The README and the three logs in docs/ record this feature. (roadmap, S2, S3, S7, N14; CLAUDE.md)

## Items the sources do not cover

Each item below was my proposal. The user answered each one.

- G1. **Agreed with a change.** The settings packet is a Server-Sent Event with the line `event: update`. The user chose the event name `update`, and I read ":update" in the answer as that name. Its data is one compact JSON object with the same four fields as the admin response, such as `{"samples_per_second":20000,"batch_interval_ms":50,"max_value":10000,"paused":false}`. The event has no `id` line. A batch event keeps its form, with no `event` line and with an `id` line. The settings packet is the first event on each connection. The server sends it again after each `PATCH /admin/settings` that returns status 200, and after a pause or a resume that changes the pause state. A pause while paused and a resume while running send no packet. When two changes happen before a client reads the first one, the client gets one packet with the newest values. Batches that the server made before a change can still arrive after the packet, as feature 6 found.
- G2. **Agreed.** The badge shows Live when the stream opens, and it changes to Paused when a settings packet says the pause is on. So a client that connects during a pause shows Live for a moment before it shows Paused. While the state is Paused, the watchdog is off. A batch that arrives during a pause still goes into the counts and does not start the watchdog. A settings packet with the pause off sets the state to Live and starts the watchdog. When the stream drops during a pause, the state is Reconnecting, and the client reconnects with the backoff from feature 4.
- G3. **Agreed with a change.** The missed batch count starts at 0 when the page loads. The first batch sets the last id and adds nothing. For each later batch, an id that is more than 1 above the last id adds `id - last id - 1` to the count. An id equal to the last id changes nothing. The client keeps the last id and the count across a reconnect, so the batches that the server sent during a drop go into the count. A pause adds nothing, because the id does not advance during a pause. The user chose that a change to N sets the count to 0, as it does for the samples received. The client keeps the last id through that reset, so the next batch adds nothing. One limit stays. After a server restart, the client adds a false gap when the first new id is higher than the last id it saw. This needs a server that ran for less time than the client took to reconnect.
- G4. **Agreed with a change.** I proposed the blue info tone from the HTML design. The user chose the neutral tone, which is the white badge that Connecting uses. The Paused badge shows the Material Symbols icon `pause`. The Google Fonts link in frontend/src/index.html adds `pause` to its icon list. The styles need no new color.
- G5. **Agreed with a change.** I proposed one readout for the missed batches and a compact group of three small rows for the settings. The user chose four full readouts. The side panel adds them between Max count and Frame rate, in the same style and with a line between them. The labels are "Missed batches", "Samples per second", "Batch interval", and "Max value", in that order. **Changed by the user in review:** I first put the four readouts below Frame rate. The user moved Frame rate to the bottom of the panel, and put the label above the value in each readout. The values look like 0, 20,000, 50 ms, and 10,000. The numbers use the same format as the other readouts, and "ms" is a unit as "fps" is. The three settings readouts do not show until the client has the settings, so the panel shows no made-up values while the state is Connecting.
- G6. **Agreed.** With the test source, the three settings readouts show the `rate`, `interval`, and `max` values of the test source. The Missed batches readout does not show, because the worker messages carry no sequence number.
- G7. **Agreed.** The new client code goes in these files. frontend/src/app/source/missed-batches.ts holds a small class that takes each batch id and returns the count. frontend/src/app/source/stream-status.ts adds the `paused` state, a signal for the three settings, and a signal for the missed batch count. The source in use writes them, and the panel reads them. On the server, the broadcaster keeps the current settings packet, and the packet and the admin response share one model.
