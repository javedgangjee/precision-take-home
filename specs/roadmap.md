# Roadmap

Every feature updates the README and the three logs in docs/ as it goes. That work covers S1 to S7 and N14 across all features.

1. **Scaffold.** The goal is a repo where the backend, the frontend, and the CDK app exist, the tests run, the linters pass, and the CDK app synthesizes, all from the Makefile. It covers N13 and S2. The status is done.
2. **Backend.** The goal is a FastAPI server that generates random integers and sends them in batches over Server-Sent Events. The backend allows cross-origin calls with CORSMiddleware. It reads the allowed origins from an environment variable, and the default is http://localhost:4200. It covers B2, N5, N7, N8, and N11. The status is done.
3. **Frontend.** The goal is an Angular client that bins values, keeps counts, and draws the grid, the axis labels, the color scale, and the side panel. It covers B1, B3, B4, B5, B6, N1, N2, N3, N4, D2, and D3. The status is done.
4. **Stream.** The goal is a client that shows the stream state, reconnects with backoff, and keeps counts on screen during a reconnect. The feature also adds a Dockerfile for the backend and a Makefile target that runs the stream in Docker Desktop on my laptop, so the client can connect to the same image that feature 5 deploys. It covers N9, N10, and D1. The status is done.
5. **Deploy.** The goal is the backend running on ECS Fargate behind an ALB at my domain, deployed with CDK from the Makefile. It covers B2 and N13. The status is done.
6. **Admin API.** The goal is a set of backend HTTP endpoints that change the stream settings while the server runs, so that a test of a new sample rate needs no restart. The feature has no admin web page. An HTTP request sets the samples per second, the batch interval, and the maximum value, within the ranges in N11. An HTTP request can also pause and resume the generation. While paused, the server sends no batches, the batch sequence number does not advance, and the server heartbeat keeps each connection alive. The feature sends no new events to the client and changes no client code. It covers no required item. The status is planned.
7. **Settings Display.** The goal is a client that shows the live stream settings, the pause state, and the batches it missed. When a client connects, the server sends it an init packet with the samples per second, the batch interval, and the maximum value. When a setting changes, the server sends every client an update packet with the same three settings. The side panel shows the three settings and updates them when an update packet arrives. When the pause state changes, the server sends every client a pause event that says whether the generation is paused. A client that connects during a pause gets the pause event when it connects. A client that gets a pause event for a pause stops its 5 s watchdog, keeps the stream open, and shows Paused in the badge. A pause event for a resume starts the watchdog again. The client reads the batch sequence number from each event id and counts the batches it missed, both inside one connection and across a reconnect. When an id skips ahead, the client adds the size of the gap to the missed batch count. When an id is lower than the last one, the server has restarted, and the client resets the missed batch count to 0. The side panel shows the missed batch count. It covers N10 for the Paused state and N5 for the missed batch count, and no other required item. The status is planned.
8. **Testing.** The goal is a measured generation-to-render latency and a measured set of limits from a stress test. The feature also has a tuning step, in which I change the server settings with the admin API from feature 6 while the server runs. The tuning step finds the highest samples per second, and the batch interval for it, that still meets the 100 ms latency target in N6 and keeps the client at 54 fps or more, and that rate becomes the new default. The tuning step also finds the batch interval that gives the lowest generation-to-render latency at the default rate. The feature writes docs/results.md, which breaks down the findings and the tuned settings. It covers N6 and N12. The status is planned.
9. **Submission Check.** The goal is a repo that holds every document the submission needs, checked against the brief and the project overview. I add the documents to the repo, including the write-ups for B7 and B8. The AI then checks each requirement in the brief and the project overview against the repo and writes docs/submission-checklist.md. The checklist gives each requirement, the file that meets it, and a status of met or missing. The AI does not write the missing documents. It covers the check of B7, B8, and S1 to S7. The status is planned.
