# Feature 3 requirements: Frontend

## Requirements from the sources

- R1. The client renders an N by N grid on a canvas, and N is configurable. (B1; tech-stack.md, Frontend)
- R2. N ranges from 1 to 64, and the default is 32. When N changes, all counts reset to zero. (N3)
- R3. The client bins each value with index = (v - 1) mod N², row = index div N, and column = index mod N. For a 4 by 4 grid, 17 goes to cell <0,0>, 8 goes to cell <1,3>, and 0 goes to cell <3,3>. (B3, N1)
- R4. Row 0 is at the bottom of the grid, and column 0 is at the left. (N1)
- R5. Each cell keeps a running cumulative count of hits as a 64-bit float. (B4; tech-stack.md, Frontend)
- R6. The color position of a non-empty cell is (count - 1) / (max - 1). A count of 1 gets the blue end of the scale, the max count gets the red end, and a cell with zero count has no color. When the max count is 1, every non-empty cell gets the blue end. G3 sets the end colors. (B5, N4)
- R7. A color scale beside the grid shows the colors from blue to red, with labels that run from 1 at the bottom to the max count at the top. (B5, N4; brief picture item d)
- R8. The grid shows row numbers on the left and column numbers along the bottom. When N is too large to label every row and column, the labels appear at a fixed interval. (N2)
- R9. The client applies each batch to the counts when the batch arrives, and it redraws at most once per display frame with requestAnimationFrame. The grid and the color scale update in real time. (B6; tech-stack.md, Frontend)
- R10. The side panel has minus and plus buttons that change N. (D2)
- R11. The side panel shows the samples received, the max count, and the measured frame rate. (D3)
- R12. The layout, colors, fonts, and spacing follow the HTML design, except where the brief or the specs differ. (tech-stack.md, Frontend; CLAUDE.md)
- R13. A test source in the browser makes batches of uniform random integers, so that the user can stress test the browser and watch the frame rate before feature 4 connects the server. (user request for this feature; N11, N12)
- R14. The README and the three logs in docs/ record this feature. (roadmap, S3, S7, N14; CLAUDE.md)

## Where the brief and the specs override the HTML design

- The HTML design allows N from 4 to 100. The client uses 1 to 64 (N3).
- The HTML design has no row or column labels. The client adds them, as in the brief picture (N2).
- The HTML design colors a cell by count / max on a jet scale from dark blue to dark red. The client uses (count - 1) / (max - 1) on the scale in G3 (N4).
- The HTML design draws row 0 at the top. The client draws row 0 at the bottom (N1).
- The HTML design shows a fixed "30 fps". The client measures the frame rate (D3).
- The HTML design has a stream status badge. Feature 4 adds it (D1), so this feature leaves it out.

## Items the sources do not cover

Each item below was my proposal. The user answered each one.

- G1. **Agreed.** The test source reads its settings from the URL query, as the user chose. The names are `rate` for samples per second, `interval` for the batch interval in ms, and `max` for the maximum value. An example is http://localhost:4200/?rate=1000000&interval=50&max=1024. A change needs a reload, which also resets the counts. The defaults match the server, which are 100,000 samples per second, 50 ms, and 1,024. The interval and the max value have the server ranges. The rate goes up to 10,000,000 so that the stress test can go past the server limit. A value that is out of range or not a number falls back to its default, and the client logs a warning to the console.
- G2. **Agreed.** The test source runs in a Web Worker. The worker makes each batch, encodes it to a JSON string, and posts the string to the main thread. The main thread parses the string and bins the values. This matches the cost on the main thread of the SSE path in feature 4, where the browser receives text and the client parses it. The generator carries the fractional sample count to the next batch, as the server does (feature 2, G4). In this feature the test source always runs. Feature 4 decides how the user picks the test source or the server.
- G3. **Agreed with a change.** The user widened the scale at both ends to make the colors easier to tell apart. The blue end is #1E00FF, which is hue 247°, and the red end is #FF0033, which is hue 348°. The map sweeps the hue from 247° down through cyan, green, and yellow to 348°, at full saturation and full brightness, in equal steps of hue. The hue span is 259°, where the jet map without its dark ends spans 240°. The colors at the thirds of the scale are #00FFAD and #C2FF00. A 256-entry table holds the colors. The scale bar uses `linear-gradient(to top in hsl longer hue, #1E00FF, #FF0033)`, which follows the same hue path, so the bar and the cells match. N4 in specs/mission.md says full blue and full red. The replan step updates it to name these end colors. In the brief picture, cell (b) with count 5 of 10 looks yellow. This map makes it green, at #00FF33. I treat the picture colors as a sketch.
- G4. **Agreed with a change.** The user simplified the scale labels. When the max is 2 or more, the scale shows three labels. They are the max at the top, the midpoint (max + 1) / 2 at the middle, and 1 at the bottom. The midpoint shows one decimal place when it is not a whole number, such as 5.5 for a max of 10, so the label matches its place on the bar and never repeats the max or 1. When the max is 1, the scale shows only 1. When the max is 0, it shows no labels. The numbers use en-US digit groups, such as 1,024.
- G5. **Agreed.** The axis label step is 1 when N is 16 or less, 2 when N is 17 to 32, and 4 when N is 33 to 64. The client labels each row and column whose number is a multiple of the step, so a 64 by 64 grid shows 16 labels on each axis. The client draws the labels on the same canvas as the cells, so they stay lined up with the cells at any size.
- G6. **Agreed.** The frame rate is the number of requestAnimationFrame callbacks in the last full second. The loop runs on every frame, and it draws the grid only when the counts or the size changed. When the main thread is too busy to keep up, the frame rate drops, which is what the stress test must show.
- G7. **Agreed with a change.** The panel readouts update at most once every 150 ms, as the HTML design does, so text updates do not cost a frame. The grid itself redraws on each frame that has new data. **Added by the user:** A red error line shows below the frame rate readout when the frame rate drops below the expected rate. The expected rate is the highest one-second reading since the page loaded, as the user chose. On an idle page this is the display refresh rate, so the rule works on 60 Hz and 120 Hz screens. The line shows when the reading is below 90 percent of that peak, and its text is "Below the expected 60 fps" with the peak in place of 60. The line uses the design token --danger-text, which is #B33A3A and has a contrast ratio of 5.9 to 1 on the white panel. That passes WCAG AA for small text. The line hides again when the reading is back at or above 90 percent of the peak. It follows the same 150 ms update as the readouts.
- G8. **Agreed with a change.** The N control follows the HTML design. It has a minus button, a read-only field that shows "32 × 32", and a plus button. The user asked that a button hide instead of going disabled. The minus button is hidden at 1, and the plus button is hidden at 64. A hidden button uses `visibility: hidden`, so it cannot be clicked or reached with Tab, and it keeps its space so the field does not move. The up and down arrow keys in the field change N by 1, and with Shift by 10.
- G9. **Agreed with a change.** The fonts are Red Hat Display, Libre Franklin, and IBM Plex Mono, as in the HTML design. The implement step extracts the six woff2 files from the design bundle into frontend/public/fonts/, so the client needs no network for fonts. The client uses the light theme only. The repo is private and will not be released, so it has no license files for the fonts, as the user asked.
- G10. **Agreed with a change.** The user asked for thin components, with the heat map state in its own unit, and for the grid to be drawn on a canvas. The heat map state lives in one injectable service, the store. It owns N, the counts, the frame rate meter, the dirty flag, and the readout signals. It is the only code that changes them. The drawing lives in a plain renderer class with no Angular code, which draws the cells and the axis labels on a 2D canvas context. The components only bind signals from the store and forward user events to it. The heat map component hosts the canvas, watches its size, and runs the requestAnimationFrame loop that calls the store and the renderer. The color scale component shows the bar and its labels. The side panel component shows the N control and the readouts. The new code lives in frontend/src/app/ in three folders. The heatmap/ folder holds the binning, the counts, the color map, the layout, the frame rate meter, the store, the renderer, the heat map component, and the color scale component. The panel/ folder holds the side panel component. The source/ folder holds the test source settings, the batch generator, the worker, and the service that starts the worker.
