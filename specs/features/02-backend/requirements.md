# Feature 2 requirements: Backend

## Requirements from the sources

- R1. The server streams nonnegative integers to the client over Server-Sent Events. (B2; tech-stack.md, Backend)
- R2. The server sends the stream in batches, and each batch is a JSON array of random integers from a uniform distribution. (N5)
- R3. The server generates one shared stream, and every connected client gets the same batches. (N5)
- R4. Delivery is lossy and best effort. The server does not buffer or replay batches for a slow or disconnected client. (N7; trade-offs.md, constitution)
- R5. The server sends a heartbeat when it has sent nothing for 15 seconds. (N8)
- R6. The server reads samples per second, the batch interval, and the maximum value from environment variables at start. Samples per second range from 1 to 100,000, the batch interval ranges from 50 ms to 1 s, and the maximum value is at most 10,000. The defaults are 5,000 samples per second and a 50 ms batch interval, so each default batch holds 250 integers. (N11)
- R7. The server allows cross-origin calls with CORSMiddleware. It reads the allowed origins from an environment variable, and the default is http://localhost:4200. (roadmap feature 2)
- R8. The `GET /health` endpoint still returns `{"status": "ok"}`. (feature 1, G2)
- R9. The README and the three logs in docs/ record this feature. (roadmap, S3, S7, N14; CLAUDE.md)

## Items the sources do not cover

Each item below was my proposal. The user answered each one.

- G1. **Agreed.** The stream endpoint is `GET /stream`. It is an async generator route declared with `response_class=EventSourceResponse`, the built-in SSE support in FastAPI 0.142.1. The router, not the response class, adds the keep-alive, so the route must yield its batches and must not return a response object. Each batch is one SSE event with no event name, and its data field is the JSON array. The event `id` field holds the batch sequence number. The sequence number starts at 0 when the server starts and goes up by 1 for each batch the server makes, so a client can count the batches it missed. The server ignores the `Last-Event-ID` header on a reconnect, because delivery is lossy. The sequence number goes back to 0 when the server restarts. The user added the sequence number to this item. The broadcaster encodes each batch to JSON once with `json.dumps`, and every client gets the same string. The route yields `ServerSentEvent(raw_data=text, id=str(seq))`, so FastAPI does not encode the batch again for each client. When the route passes the list as `data`, FastAPI encodes it with `jsonable_encoder` for each client, which took 2.94 ms per 5,000-value batch. One `json.dumps` took 0.28 ms. The user approved the single encode. The built-in keep-alive sends the comment `: ping` after 15 idle seconds, which meets R5 with no extra code.
- G2. **Agreed with a change.** Each value is a uniform random integer from 0 to the maximum value minus 1. The generator makes each batch with `random.Random.choices(range(max_value), k=n)` from the Python standard library, as the user asked. The project does not use NumPy. A 5,000-value batch took 0.48 ms with `choices`, 1.55 ms with a `randrange` loop, and 2.21 ms with a `randint` loop on my laptop. The maximum value is set by an environment variable, ranges from 1 to 10,000, and defaults to 1,024, as the user asked. The default matches the default grid of 32 by 32. With the range 0 to 1,023, the default grid fills evenly. The range 0 to 1,024 would send both 0 and 1,024 to cell <31,31>, and that cell would get twice the hits of the others.
- G3. **Agreed with a change.** The environment variables are `SAMPLES_PER_SECOND`, `BATCH_INTERVAL_MS`, `MAX_VALUE`, and `CORS_ORIGINS`. `CORS_ORIGINS` is a comma-separated list. A Pydantic model checks the values, so the project needs no new dependency. When a value is out of range or not a number, the server logs a warning that names the variable and uses the default for it, as the user asked. The server still starts.
- G4. **Agreed.** When samples per second times the interval is not a whole number, the server carries the fraction to the next batch. For example, 1 sample per second at 50 ms gives one value in every 20th batch. The server does not send an empty batch, so the heartbeat covers the idle time.
- G5. **Agreed with a change.** One background task starts with the app and makes each batch. Each client has its own queue that holds at most 2 batches, which is 0.1 s at the default interval. The user chose 2 over 10 to try first, because 10 batches add up to 0.5 s of delay. When a queue is full, the server drops the oldest batch in it, so a slow client gets fresh data and never slows the others.
- G6. **Agreed.** The generator schedules each batch from a fixed start time on the monotonic clock, so the batches do not drift when one batch takes longer to make.
- G7. **Agreed.** The stream tests run the app in a real Uvicorn server on a free local port and read the stream with an HTTP client. The in-process test clients can wait for the end of a response, and this stream has no end.
